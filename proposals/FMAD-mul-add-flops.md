# FMAD: Fused Multiply-Add via `suboptimal_flops`

## Problem

Clippy's `suboptimal_flops` (nursery) flags 75 sites in this codebase where `a * b + c` could be written as `a.mul_add(b, c)`. On FMA-capable hardware (Apple Silicon NEON FMA, x86 with FMA3) `mul_add` compiles to a single fused instruction that:

- Is **more accurate** — one rounding step instead of two.
- Is **faster** — one instruction instead of two (often 1 cycle vs 2–3).

Hotspots observed in the `-W clippy::nursery` run:

- `src/scf/smearing.rs` — Fermi-Dirac / Methfessel-Paxton kernels (19 `as`-cast sites, heavy arithmetic).
- `src/potential/xc.rs` — LDA exchange-correlation energy/potential expressions.
- `src/ewald.rs` — Real-space and reciprocal-space Ewald sums.
- `tests/kb_projector_validation.rs` — Legendre polynomial recurrences (lines 82–83).

Example from the clippy run:

```rust
// tests/kb_projector_validation.rs:82
2 => 0.5 * (3.0 * x * x - 1.0)                 // before
2 => 0.5 * (3.0 * x).mul_add(x, -1.0)          // after
```

## Research

**The catch:** FMA changes bit-exact results. A single fused rounding can differ in the last bit (or a few ULPs over long sums) from the two-rounding baseline. This matters for a DFT solver because:

1. Cross-validation tolerances against QE 7.5 (`tests/free_electron_bands.rs`, `tests/kb_projector_validation.rs`, SCF energy checks) are tuned to current CPU behavior.
2. Anderson/Broyden mixing and Fermi-Dirac occupations can amplify tiny perturbations early-iteration, though they should converge to the same fixed point.
3. GPU-vs-CPU consistency tests (`gpu_cpu_consistency` integration tests) may need re-calibration if CPU switches to FMA while GPU shaders do not.

Prior art: QE itself uses FMA-friendly compiler flags and reports energies to ~1e-10 Ry. Our current tolerances (relative_eq with epsilon ~1e-8 to 1e-10) should absorb the ULP-level changes, but this needs empirical confirmation.

## Implementation

Treat this as a **single focused PR**, reviewed by the Researcher.

1. Enable the lint:

   ```toml
   [lints.clippy]
   suboptimal_flops = "warn"
   ```

2. Apply `cargo clippy --fix --allow-dirty --allow-staged --all-targets` — the fix is fully auto-generated by clippy.

3. Re-run the full test suite:

   ```bash
   cargo test                              # all 177 CPU tests
   cargo test --features gpu               # all 186 tests incl. GPU consistency
   ```

4. Re-run QE cross-validation:

   ```bash
   cargo test --test free_electron_bands
   cargo test --test kb_projector_validation
   ```

5. For SCF convergence tests, record before/after total energies on Si, Fe, C-diamond. Tolerance delta should be within existing `epsilon` bounds. If not, widen tolerances *only* with Researcher sign-off documenting the FMA source of the change.

6. If any test requires tightening an epsilon (FMA gives *more* accuracy), tighten it.

## Verification

- `cargo clippy -q --all-targets` — zero warnings.
- Full test suite + GPU passes.
- Before/after total-energy comparison on Si, Fe, C-diamond within relative 1e-10.
- No test `epsilon` values loosened without a documented physics reason.

## Notes

If FMA turns out to break GPU↔CPU consistency meaningfully, the fallback is to `#[allow(clippy::suboptimal_flops)]` inside any module that feeds GPU shaders (to keep bit-patterns aligned) while keeping the lint enabled for the rest of the codebase. Decide this empirically, not preemptively.
